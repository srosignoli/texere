# Themes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Three selectable themes — Blue (default), Dark and Light — chosen from a `⚙` popover in the action bar and persisted in `config.json`.

**Architecture:** A semantic token layer on `:root`, overridden per theme under `[data-theme="dark"]` and `[data-theme="light"]`. Blue's token values are byte-identical to today's literals, so the 900-literal migration is a visual no-op and can be verified as one. Go owns the persisted value; a pre-paint inline script in `index.html` reads a `localStorage` mirror so a stored theme cannot flash blue on launch.

**Tech Stack:** Go 1.25 (config + two bindings), Svelte 3.49, Vite 3, `node --test` for the pure JS. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-08-12-themes-design.md`

## Global Constraints

- **Blue must look exactly as it does today, at every step.** Each Blue token value is byte-identical to the literal it replaces. A migration pass that changes a rendered pixel in Blue has a bug, not an improvement.
- **No new dependencies.**
- **`color-scheme` flips with the theme.** `:root` keeps `color-scheme: dark` for Blue and Dark; `[data-theme="light"]` sets `color-scheme: light`. This is load-bearing — `style.css:17-20` records that WebKitGTK themes native `<select>` popups and scrollbars from it, and without it a light-mode select renders light-on-light.
- **Semantic colours stay literal.** An error red, the amber reminder banner, the chart series colours and the explorer's edge/territory hues mean the same thing in every theme. Whoever migrates a file decides which of its colours are semantic and records the decision with a reason; a colour left literal is a choice to be defended, not an omission.
- **The explorer's edge, node and territory hues do not change.** Only `--explorer-ground`, `--explorer-label`, `--explorer-label-halo`, `--explorer-plane-*` and `--explorer-extended-plane-*` get per-theme values.
- **`normalizeTheme` is the only place the default lives.** Go, the bootstrap script and the picker must not each carry their own idea of what an unset theme means.
- **Theme ids are exactly** `blue`, `dark`, `light`. Labels exactly `Blue`, `Dark`, `Light`.
- **Pure logic goes in `frontend/src/lib/`.** `make test-js` runs `node --test frontend/src/lib/*.test.js`; a module importing a `.svelte` file, a store or `wailsjs` cannot load there. `frontend/src/stores/` is for stores that may import bindings and is not covered by tests.
- **Every test must be proven able to fail.** Each test step names the production change that breaks it; make that change, watch the test fail for that reason, then revert. A test that passes against a gutted implementation is worse than no test.

```go
// validThemes is the closed set SetTheme accepts. The value reaches the DOM as
// a data-theme attribute, so an arbitrary string must never be storable.
var validThemes = map[string]bool{"blue": true, "dark": true, "light": true}

// GetTheme returns the persisted theme, defaulting to "blue" for a config that
// has none — first run, or an upgrade from before this field existed.
func (a *App) GetTheme() string {
	cfg, err := loadConfig()
	if err != nil || cfg.Theme == "" || !validThemes[cfg.Theme] {
		return "blue"
	}
	return cfg.Theme
}

// SetTheme persists the theme. An unrecognised value is rejected and the stored
// theme is left untouched.
func (a *App) SetTheme(theme string) error {
	if !validThemes[theme] {
		return fmt.Errorf("unknown theme %q", theme)
	}
	cfg, err := loadConfig()
	if err != nil {
		cfg = &AppConfig{}
	}
	cfg.Theme = theme
	return saveConfig(cfg)
}
```

Add any imports the file does not already have (`fmt`, and `strings` in the test).

```js
// The selectable themes.
//
// normalizeTheme is the ONLY place the default lives. Go returns "" for a
// config written before this field existed, the pre-paint bootstrap in
// index.html reads whatever localStorage holds, and the picker reads the store
// — none of them may carry their own idea of what an unset theme means.
//
// Dependency-free so it runs under `node --test`.

export const THEMES = Object.freeze([
  Object.freeze({ id: 'blue', label: 'Blue' }),
  Object.freeze({ id: 'dark', label: 'Dark' }),
  Object.freeze({ id: 'light', label: 'Light' }),
])

export function isValidTheme(v) {
  return typeof v === 'string' && THEMES.some((t) => t.id === v)
}

export function normalizeTheme(v) {
  return isValidTheme(v) ? v : 'blue'
}
```

- [ ] **Step 7: Add the pre-paint bootstrap to `index.html`**

Before the `<script src="./src/main.js" type="module">` line:

```html
<script>
  // Runs before first paint so a stored theme cannot flash blue: style.css
  // paints html's background immediately, and a Wails binding cannot be read
  // synchronously. config.json remains authoritative — the app reconciles this
  // mirror from Go on startup.
  try {
    var t = localStorage.getItem('texere.theme')
    if (t === 'dark' || t === 'light') document.documentElement.dataset.theme = t
  } catch (e) {}
</script>
```

Blue needs no attribute — it is `:root`'s own values — so the script acts only for the two themes that differ, and a `localStorage` failure leaves the default.

### Tasks 3-5: Migrate the components

Three passes over the 56 components carrying colour literals. **Every pass has the same shape**, which is written out once here and referenced by each task — read this section before starting any of them.

**The method, for each file in the pass:**

1. Replace each colour literal with the role token whose Blue value is byte-identical.
2. If no token matches, decide: is this colour *semantic* (it means error / warning / a chart series / an arrow meta-type, and means the same in every theme) or is it *thematic* (it is chrome that must change with the theme)? Semantic colours stay literal. A thematic colour with no matching token means the token layer is missing a role — add it to all three theme blocks in `style.css` rather than approximating with a near-match.
3. Never change a Blue value to "tidy" it. `#2a3a4a` and `#2a3a4b` in two files both become `--border` **only if** they are genuinely the same colour; if they differ by a digit, keep the difference — that is a separate task's problem, not a licence to change rendering here.

**The verification, for each pass:**

- `grep -o '#[0-9a-fA-F]\{3,8\}' <each file in scope>` and account for **every** remaining literal in your report: which token it should have been, or why it is semantic. An unexplained leftover is an incomplete migration.
- Build and run the app, screenshot the surfaces this pass touches, and pixel-diff against screenshots from the previous commit. Expect no difference. Record the diff output and the screenshot paths.
- `cd frontend && npx vite build` clean; `make test-js` passing.

**What "no difference" means:** identical, not "close". A one-pixel shift from a splitter landing differently between runs is acceptable and must be explained in the report; a changed colour value anywhere is a defect in this task.
